JWT
JSON Web Token — stateless access token

What is a JWT?

A JWT is a compact, self-contained token that carries information (called claims) inside itself. The server does not need to query a database to validate it — it just verifies the signature.

💡
Stateless by design

All the information the server needs (who the user is, when the token expires) lives inside the token. No DB lookup on every request.

Session vs JWT

Before JWT, servers used sessions. Understanding the difference explains why JWT was invented.

Traditional Session Auth
User logs in
↓
Server creates session
↓
Session stored in DB / Redis
↓
Server returns session ID
↓
Client sends session ID on every request
↓
Server looks up session in DB every time
↓
Access granted

Every request hits the database. Harder to scale across multiple servers.

JWT Auth
User logs in
↓
Server verifies credentials
↓
Server generates JWT — nothing stored
↓
Client stores JWT
↓
Client sends JWT on every request
↓
Server verifies signature — no DB needed
↓
Access granted

No DB lookup per request. Scales easily — any server can verify the token.

Structure

A JWT has three parts separated by dots: header.payload.signature

eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiJ1c2VyMTIzIn0  .  abc123xyz
        ↑                          ↑                         ↑
     Header                     Payload                  Signature
  (algorithm)               (claims/data)             (tamper-proof)

Header

{
  "alg": "HS256",
  "typ": "JWT"
}

Payload (claims)

The actual data. Anyone can decode this — never store passwords or secrets here.

{
  "sub":  "user@example.com",  // subject — who this token belongs to
  "iat":  1716000000,          // issued at (unix timestamp)
  "exp":  1716003600,          // expires at (1 hour later)
  "role": "USER"                // custom claim — anything you need
}

The exp claim is not a timer — it is just a number stored inside the token. The server reads it and compares it with the current time on every validation. If you don't set it, the token never expires.

Signature

HMACSHA256(
  base64url(header) + "." + base64url(payload),
  "your-secret-key"
)
⚠️
Payload is NOT encrypted

It is only base64-encoded — anyone can decode it. The signature proves it was not tampered with, it does not hide the data.

How the signature actually works

This is the most important concept in JWT. Most beginners get confused here — so read carefully.

Secret key ≠ Signature

The most common confusion when first implementing JWT:

❌ Wrong mental model

Secret key is the signature

The token contains the secret directly

Validating = comparing secrets

✓ Correct mental model

Secret key is the input

Signature is the output of the algorithm

The secret never leaves the server

How the signature is generated

Header  +  Payload  +  Secret Key
↓
HS256 Algorithm runs
↓
Signature = XYZ123
↓
Final JWT: HEADER.PAYLOAD.XYZ123 
// Analogy — think of it like baking:
Secret Key  =  ingredient  ("my-secret-key")
Signature   =  output      ("XYZ123")

// Flour ≠ Bread. The flour goes IN to produce the bread.
// Secret ≠ Signature. The secret goes IN to produce the signature.

What happens when an attacker tampers with the payload

This walkthrough shows exactly why JWT is tamper-proof — even though the payload is readable by anyone.

1
Server creates the original token 
Payload: { "sub": "user@example.com", "userId": 1 }
Secret:  "my-secret-key"

HS256(Header + Payload + Secret)  →  Signature = XYZ123

Token:  HEADER . PAYLOAD . XYZ123
2
Attacker decodes the payload

Remember — payload is only base64-encoded, not encrypted. Attacker can read it freely. They see userId: 1 and change it to userId: 999.

// Attacker modified payload:
{ "sub": "user@example.com", "userId": 999 }

// But they don't know the secret, so they can't regenerate the signature.
// They keep the OLD signature and send:
Token:  HEADER . NEW_PAYLOAD . XYZ123  ← old signature, new payload
3
Server recomputes the signature

The server never trusts the incoming signature. It always recomputes from scratch using its secret.

HS256(Header + NEW_PAYLOAD + Secret)  →  ABC999

Compare:
  Token signature     =  XYZ123
  Computed signature  =  ABC999
  Match?  NO  →  SignatureException  →  401 Unauthorized
✅
Claims are only trusted AFTER signature verification

The server never reads userId, role, or sub from the token until the signature check passes. Verification always happens first.

Auth flow

Client sends username + password
↓
Server verifies credentials
↓
Server generates JWT and returns it
↓
Client stores JWT (memory or HttpOnly cookie)
↓
Client sends JWT in every request header
↓
Server verifies signature — no DB needed
↓
Access granted if valid and not expired

JJWT dependencies

JJWT is split into three separate jars. You need all three — missing any one of them will cause runtime errors even if the code compiles fine.

<!-- pom.xml -->
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>0.12.6</version>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-impl</artifactId>
    <version>0.12.6</version>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-jackson</artifactId>
    <version>0.12.6</version>
    <scope>runtime</scope>
</dependency>
jjwt-api
  • The public interface you write code against
  • Contains Jwts, Claims, JwtBuilder
  • This is what IntelliJ autocompletes from
jjwt-impl
  • The actual implementation behind the interfaces
  • Without this, you get NoClassDefFoundError at runtime
  • Marked runtime — not needed at compile time
jjwt-jackson
  • Handles JSON serialisation of the payload
  • Converts Java objects ↔ JSON internally
  • Without this, claims won't serialize correctly
Why runtime scope?
  • Your code only calls the jjwt-api interfaces
  • jjwt-impl and jjwt-jackson are loaded at runtime via service discovery
  • Keeping them runtime prevents accidentally depending on internal classes

The signing key — what getSigningKey() actually does

You'll see getSigningKey() called in every JWT example, but beginners rarely know what's inside it. Here it is.

private SecretKey getSigningKey() {
    byte[] keyBytes = secretKey.getBytes(StandardCharsets.UTF_8);
    return Keys.hmacShaKeyFor(keyBytes);
}
1
secretKey is your raw string from application.properties

Something like "my-super-secret-key-32-chars-min" injected via @Value. It is a plain Java String.

2
.getBytes(StandardCharsets.UTF_8) — String → byte[]

Signing algorithms work on raw bytes, not on Java Strings. UTF-8 encoding converts each character of your secret into its byte representation consistently across all platforms.

3
Keys.hmacShaKeyFor(keyBytes) — byte[] → SecretKey

JJWT doesn't accept a raw byte array directly. It needs a SecretKey object — a Java type that wraps the bytes in a format the signing algorithm understands. Keys.hmacShaKeyFor() does that wrapping.

// Full picture:
"my-secret-key"               // String — human readable
    ↓  .getBytes(UTF_8)
byte[] keyBytes                // raw bytes — what the algorithm needs
    ↓  Keys.hmacShaKeyFor()
SecretKey signingKey           // what JJWT accepts in signWith() and verifyWith()
⚠️
Secret must be long enough

HS256 requires a minimum 256-bit (32-byte) key. If your secret string is shorter, Keys.hmacShaKeyFor() will throw a WeakKeyException at runtime. Use at least 32 characters.

Common Spring pitfall — @Value not working

This is a real bug many beginners hit when first writing JwtService.

❌ Broken — @Value does nothing
// Plain Java class — NOT a Spring Bean
public class JwtService {

    @Value("${jwt.secret}")
    private String secret;  // always null!
}

Spring only injects @Value into beans it manages. A plain new JwtService() object is invisible to Spring — the field stays null and you get a NullPointerException when you try to use it.

✓ Fixed — make it a Spring Bean
// Spring manages this class
@Service
public class JwtService {

    @Value("${jwt.secret}")
    private String secret;  // injected ✅
}

@Service tells Spring to create and manage this class. Now Spring sees the @Value annotation and injects the property value from application.properties.

💡
Rule of thumb

Any class that uses @Value, @Autowired, or @Inject must be a Spring-managed bean — annotated with @Service, @Component, @Repository, or @Controller. Without one of these, Spring doesn't know the class exists.

Generating a token (JJWT 0.12.x)

Think of Jwts.builder() as gradually configuring a token — like filling out a form. Nothing is built until you call .compact() at the very end.

public String generateAccessToken(String email) {
    Date now    = new Date();
    Date expiry = new Date(now.getTime() + 1000L * 60 * 15); // 15 minutes

    return Jwts.builder()
        .subject(email)                   // who this token belongs to
        .claim("role", "USER")           // custom claim
        .issuedAt(now)                    // iat — when it was created
        .expiration(expiry)               // exp — when it expires
        .signWith(getSigningKey(), Jwts.SIG.HS256)  // sign with explicit algorithm
        .compact();                       // ← THIS is where the token is actually built
}

What does compact() do?

This confused a lot of beginners. Jwts.builder() is just configuration — nothing exists yet. .compact() is the step that actually does the work.

Jwts.builder()
↓
.subject() .claim() .issuedAt() .expiration() .signWith()
↑ just configuring — no token exists yet
↓
.compact()
↑ builds the JWT, signs it, serializes to String
↓
"eyJhbGci... eyJzdWI... abc123" ← final JWT String 
// Without .compact() you have:
JwtBuilder builder  ← just an object, not a token

// After .compact() you have:
String token = "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOi..."  ← this is sent to the client

Validating a token (JJWT 0.12.x)

Validation is the reverse of generation. You give the parser the secret key, hand it the raw token string, and it does all the work — signature check, expiry check, structure check.

Each step explained

private Claims extractAllClaims(String token) {
    return Jwts.parser()
        .verifyWith(getSigningKey())     // Step 1 — tell parser which key to use later
        .build()                         // Step 2 — create the parser object
        .parseSignedClaims(token)        // Step 3 — actual validation happens here
        .getPayload();                   // Step 4 — extract the Claims from the result
}
1
.verifyWith(getSigningKey())

Does not verify anything yet. It just tells the parser: "when you do verify, use this key." Think of it as handing the key to the doorman before the door even opens.

2
.build()

Creates the parser object. Still no validation. Same idea as Jwts.builder() on the generation side — just setup.

3
.parseSignedClaims(token)

This is where everything actually happens. The entire validation runs inside this single call.

Split token into Header . Payload . Signature
↓
Decode Header and Payload
↓
Recompute signature using your secret key
↓
Compare computed signature vs token signature
↓
Mismatch? → throw SignatureException immediately
↓
Read exp from payload
↓
Expired? → throw ExpiredJwtException
↓
All valid → return Claims
4
.getPayload()

Returns the Claims object — a map-like object containing all the data from the payload.

What does parseSignedClaims() return?

A very common confusion — it does not return a boolean. It returns the parsed token data, which you can then read from.

var result = Jwts.parser()
    .verifyWith(getSigningKey())
    .build()
    .parseSignedClaims(token);

// result contains everything from the token:
result.getPayload().getSubject();              // → "user@example.com"
result.getPayload().getExpiration();           // → Date object
result.getPayload().get("role", String.class); // → "USER"
💡
Why return Claims and not boolean?

If it returned true/false you'd have no way to extract the user's email or role. The claims are the whole point — you need them to load the user for the request.

Why does it throw exceptions instead of returning false?

Invalid tokens are exceptional conditions. JJWT signals failure by throwing, not by returning a value. This keeps the happy path clean and forces callers to handle failures explicitly.

// Possible exceptions thrown by parseSignedClaims():
SignatureException      // payload was tampered with
ExpiredJwtException     // token is past its exp date
MalformedJwtException   // not a valid JWT format

Converting to boolean — the try-catch pattern

If your method needs to return true/false, wrap the call in a try-catch. The boolean comes from your method, not from JJWT.

public boolean validateToken(String token) {
    try {
        Jwts.parser()
            .verifyWith(getSigningKey())
            .build()
            .parseSignedClaims(token);   // throws if anything is wrong
        return true;                     // only reached if no exception
    } catch (Exception e) {
        return false;                    // tampered, expired, malformed — all → false
    }
}

// Helper methods all delegate to extractAllClaims():
public String extractUsername(String token) {
    return extractAllClaims(token).getSubject();
}
public Date extractExpiration(String token) {
    return extractAllClaims(token).getExpiration();
}
💡
Why extractAllClaims() is the foundation

extractUsername(), extractExpiration(), and validateToken() all parse the token. If each called the parser directly, you'd parse the same token 3 times per request. One extractAllClaims() method parses once, and everything else reads from it.

When the access token expires

A common misconception: the backend does not automatically call the refresh endpoint. It simply returns a 401. The frontend is responsible for detecting the 401 and deciding what to do.

Client makes API request with expired token
↓
Server parses token → ExpiredJwtException
↓
Server returns 401 Unauthorized
↓
Frontend detects 401 response
↓
Frontend calls POST /auth/refresh with refresh token
↓
Server validates refresh token → issues new access token
↓
Frontend retries the original request with new token

Two approaches to refresh

Simple (good for learning)
  • Validate refresh token
  • Issue a new access token
  • Keep the refresh token unchanged
Token rotation (production)
  • Validate refresh token
  • Delete the old refresh token
  • Issue new access token + new refresh token
  • Enables theft detection

Best practices

SettingRecommendationReason
Expiry15 min – 1 hourShort life limits damage if stolen
Secret key256-bit minimum, env varNever hardcode in source
Storage (web)Memory or HttpOnly cookielocalStorage is vulnerable to XSS
AlgorithmExplicit — Jwts.SIG.HS256Never let the library infer; makes intent clear
alg=none attackAlways use parseSignedClaims()Rejects unsigned tokens — parseUnsecuredClaims() would accept them

Bcrypt & Hashing
Password hashing — how it works, why it's safe

What is a hash function?

A hash function takes any input and produces a fixed-size output. It is one-way — you cannot reverse it.

"mySecret123"  →  [hash function]  →  "8f14e45fceea167a5a36dedd4bea2543"
// Cannot go backwards — impossible

Anatomy of a bcrypt hash

The output is one string containing version + cost + salt + hash — everything needed to verify later.

$2a$
10$
N9qo8uLOickgx2ZMRZoMye
IjZAgcfl7p92ldGxad68LJZdL17lhWy
version
cost (10 = 1024 rounds)
salt — random, stored here
actual hash
✅
Salt is stored inside the string

When bcrypt verifies a password, it reads the salt from the stored string — it does not generate a new one.

Signup flow

1
User enters password

Raw password arrives. Never store this directly.

2
bcrypt generates a random salt

Fresh random value like N9qo8uLOickgx2ZMRZoMye.

3
password + salt hashed 1024 times

Repeated mixing makes the result slow to compute.

4
One string stored in DB

Packs version + cost + salt + hash: $2a$10$N9qo...lhWy

String hash = passwordEncoder.encode("mySecret123");
user.setPasswordHash(hash);
userRepository.save(user);

Login flow (verification)

bcrypt does not generate a new salt during verify. It reads the salt from the stored string and reuses it.

1
Find user by email

Query DB by email — email finds the row, not the hash.

2
Extract salt from stored string

bcrypt reads N9qo8uLOickgx2ZMRZoMye directly from $2a$10$....

3
Rehash with the same salt

Same salt = same output if the password is correct.

4
Compare → true / false

Match → login success. No match → reject.

hash("mySecret123" + extractedSalt) = "IjZAgcfl7p92...17lhWy"  ← matches ✅
hash("wrongPassword" + extractedSalt) = "Xp92ldGx...Z7qL"       ← no match ❌

boolean valid = passwordEncoder.matches(rawPassword, user.getPasswordHash());

Rounds explained

One round = running the mixing function once. bcrypt chains rounds — output of round N feeds into round N+1.

cost 10  →  2¹⁰ =    1,024 rounds  →  ~0.3s
cost 12  →  2¹² =    4,096 rounds  →  ~1.2s
cost 14  →  2¹⁴ =   16,384 rounds  →  ~5s
Real user logging in
  • ~0.3s — invisible to the user
  • Happens once per login
Attacker brute-forcing
  • 1 million guesses = 3.5 days
  • Billions of guesses = impractical

Why bcrypt works for passwords but NOT for tokens

✓ Password login — works

Client sends: email + password

DB lookup by: email — not hash

bcrypt.verify() reads salt from stored string → rehashes → compares

✗ Refresh token — broken

Client sends: token only — no email

Must query DB by token itself

WHERE hash = bcrypt(token) → bcrypt produces a different hash every call (random salt) → 0 rows always

// SHA-256 is deterministic — same input, same output, always:
SHA256("xK9mP2qL")  →  "8f14e45f..."
SHA256("xK9mP2qL")  →  "8f14e45f..."  ← identical ✅

SELECT * FROM refresh_tokens WHERE token_hash = SHA256("xK9mP2qL");
// → 1 row found in milliseconds

Refresh Tokens
Long-lived tokens that issue new access tokens

Why two tokens?

JWTs are stateless — they cannot be revoked. So keep them short-lived (15 min – 1 hr). The refresh token is stored in DB and can be revoked, giving users a long session without sacrificing security.

Access token (JWT)
  • Short-lived: 15 min – 1 hr
  • Stateless, verified by signature
  • Sent with every API request
  • Not stored in DB
Refresh token
  • Long-lived: 7 – 30 days
  • Stored in DB as SHA-256 hash
  • Used only to get a new access token
  • Revocable — just delete the row

Design choices

OptionDB lookupRevocableVerdict
JWT as refresh tokenyesyes (via DB)works but overkill
bcrypt hashbroken—wrong tool
SecureRandom + SHA-256yesyescorrect ✓

Token rotation & theft detection

Every time a refresh token is used, delete it and issue a new one. If a rotated token is presented again, it signals theft.

Client sends refreshToken A
↓
Server looks up A in DB — found
↓
Server DELETES A from DB
↓
Server issues refreshToken B + new access token
↓
Client stores B, discards A
🔐
On token reuse — revoke everything

If an already-rotated token is presented, delete ALL tokens for that user and force full re-login.

Implementation

Entity

@Entity
public class RefreshToken {
    @Id @GeneratedValue
    private Long id;
    @Column(nullable = false, unique = true)
    private String tokenHash;   // SHA-256 of raw token
    @ManyToOne private User user;
    private Instant expiresAt;
    private boolean revoked;
}

On signup / login

byte[] bytes = new byte[64];
new SecureRandom().nextBytes(bytes);
String rawToken   = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
String tokenHash  = sha256(rawToken);
refreshTokenRepo.save(new RefreshToken(tokenHash, user, Instant.now().plus(7, DAYS)));
return new AuthResponse(accessToken, rawToken);  // raw token to client only

On POST /auth/refresh

RefreshToken stored = repo.findByTokenHash(sha256(rawToken))
    .orElseThrow(() -> new InvalidTokenException("Invalid token"));

if (stored.isExpired() || stored.isRevoked()) {
    repo.deleteAllByUser(stored.getUser());  // possible theft — revoke all
    throw new InvalidTokenException("Token reuse detected");
}

repo.delete(stored);  // rotate
return new TokenPair(
    jwtService.generateAccessToken(stored.getUser()),
    createRefreshToken(stored.getUser())
);

On logout

repo.deleteByTokenHash(sha256(rawToken));

SecureRandom
Cryptographically secure token generation

Two types of randomness

Math.random() / java.util.Random

Pseudorandom — uses a mathematical formula

Predictable if attacker knows the seed

Use for: games, simulations

java.security.SecureRandom

Uses OS-level entropy (hardware noise, timing)

Unpredictable even if attacker knows your code

Use for: tokens, session IDs, API keys

Generating a token

1
Generate 64 random bytes

1 byte = 8 bits = a value 0–255. SecureRandom fills an array of 64 such values from OS entropy.

2
Base64 URL encode → safe string

Raw bytes contain non-printable characters. Base64 gives you only A–Z, a–z, 0–9, -, _ — safe in HTTP headers, URLs, JSON.

3
SHA-256 hash → store in DB

Never store the raw token. Store the hash. If DB is breached, hashes are useless without the raw token.

// Generate
byte[] randomBytes = new byte[64];
new SecureRandom().nextBytes(randomBytes);
String rawToken = Base64.getUrlEncoder().withoutPadding().encodeToString(randomBytes);

// Hash for DB
private String sha256(String raw) {
    MessageDigest digest = MessageDigest.getInstance("SHA-256");
    byte[] hash = digest.digest(raw.getBytes(StandardCharsets.UTF_8));
    return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
}

String tokenHash = sha256(rawToken);  // → store this in DB
// rawToken → send to client only, never store
Without hashing (bad)
  • DB breach exposes raw tokens
  • Attacker can use immediately
  • All sessions compromised
With SHA-256 (good)
  • DB breach exposes only hashes
  • Cannot reverse SHA-256
  • Hashes useless to attacker

ORM & the Impedance Mismatch
Why storing Java objects in a database is not straightforward

The core problem

You have a Java object and you want to store it in a database. Sounds simple — but Java and relational databases speak completely different languages.

Java World

Thinks in Objects

A User has fields, methods, references to other objects

Relationships = object references (user.getOrders())

Inheritance, polymorphism, encapsulation

Database World

Thinks in Tables and Rows

A users table has columns — no methods, no behaviour

Relationships = foreign keys and joins

No inheritance, no polymorphism

// Java — you think like this:
User user = new User(1L, "Ishant");
user.getOrders();   // reference to a List<Order>

// Database — it thinks like this:
// users table
// | id |  name  |
// |  1 | Ishant |

// orders table
// | order_id | amount | user_id |   ← foreign key back to users.id
// |     101  |  500   |    1    |

The mismatch map

Object Class Field Object reference Inheritance
↔↔↔↔↔
Row Table Column Foreign Key No direct equivalent

This gap between the two worlds is called the Object Relational Impedance Mismatch. Every tool in the Java database ecosystem — JDBC, Hibernate, JPA, Spring Data JPA — exists to bridge it.

What is ORM?

ORM stands for Object Relational Mapping. It is the technique of automatically converting between Java objects and database rows so you don't have to write that conversion code yourself.

Java Object: User(id=1, name="Ishant")
↓  ORM converts automatically
SQL: INSERT INTO users VALUES (1, 'Ishant')
↓
Row stored in database 
// Without ORM — you write all this yourself every time:
String sql = "INSERT INTO users(id, name) VALUES (?, ?)";
PreparedStatement stmt = conn.prepareStatement(sql);
stmt.setLong(1, user.getId());
stmt.setString(2, user.getName());
stmt.executeUpdate();

// With ORM — one line:
repository.save(user);

What is a relational database?

A relational database stores data in tables. Tables have rows and columns. Tables can be related to each other using keys.

Primary key

Uniquely identifies a row in a table. No two rows can have the same primary key.

-- users table
| id  | name   |
|-----|--------|
|  1  | Ishant |   ← id is the primary key
|  2  | John   |

Foreign key

A column in one table that points to the primary key of another table. This is how relationships are expressed in a database.

-- transactions table
| txn_id | amount | user_id |
|--------|--------|---------|
|  1001  |  500   |    1    |   ← user_id is a foreign key → users.id
|  1002  |  200   |    1    |
|  1003  |  750   |    2    |
💡
Object reference vs Foreign key

In Java you write transaction.getUser() — a direct reference. In the DB the same relationship is transaction.user_id = users.id — a key you must JOIN on. ORM bridges this gap automatically.

Spring Boot/Data / JPA
JDBC & Spring JDBC
The lowest layer — how Java talks to a database

What is JDBC?

JDBC (Java Database Connectivity) is the standard Java API for communicating with any relational database. It is the lowest level — everything else (Hibernate, JPA, Spring Data JPA) sits on top of it.

💡
JDBC is just interfaces

JDBC itself does not know how to talk to MySQL or PostgreSQL. It only defines the contract — a set of interfaces. The actual communication is handled by a JDBC Driver specific to each database.

The four core JDBC interfaces

Connection
  • Represents an open connection to the DB
  • Everything happens through a connection
  • Must be closed after use
PreparedStatement
  • A pre-compiled SQL query
  • Use ? placeholders for parameters
  • Protects against SQL injection
ResultSet
  • Holds the rows returned by a query
  • You iterate over it row by row
  • Manually map each column to a field
DriverManager
  • Creates Connection objects
  • Loads the right driver for the URL
  • Entry point for raw JDBC

JDBC architecture

Your Application code
↓
JDBC API (interfaces — Connection, PreparedStatement, ResultSet)
↓
JDBC Driver (database-specific implementation)
↓
Database (MySQL / PostgreSQL / H2 / Oracle)

Raw JDBC example

// 1. Open a connection
Connection conn = DriverManager.getConnection(
    "jdbc:postgresql://localhost:5432/mydb",
    "username", "password"
);

// 2. Create a prepared statement
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE id = ?"
);
stmt.setLong(1, 1L);

// 3. Execute and get results
ResultSet rs = stmt.executeQuery();

// 4. Manually map columns to object fields
while (rs.next()) {
    User user = new User();
    user.setId(rs.getLong("id"));
    user.setName(rs.getString("name"));
}

// 5. Close everything (or you leak resources)
rs.close();
stmt.close();
conn.close();
😩
The JDBC pain

Every single query needs this. Open connection → create statement → set parameters → execute → iterate results → map columns → close everything. And if you forget to close, you leak connections. This boilerplate is why everything above JDBC was invented.

What is a JDBC Driver (Connector)?

JDBC only defines the contract. The driver is the actual implementation that knows how to talk to a specific database over the network.

💡
Analogy — language vs translator

JDBC is like English. Your application speaks English (JDBC). But the database speaks its own dialect. The driver is the translator that converts your English instructions into what the database actually understands.

Why do we need a driver?

Different databases use different network protocols, authentication mechanisms, and wire formats. When you send SELECT * FROM users, MySQL and PostgreSQL receive it differently over the wire. The driver handles all of that so your Java code never has to.

Your code never imports driver classes directly. You only use JDBC interfaces. The driver is loaded automatically at runtime by the JVM through the URL prefix (jdbc:postgresql://...). So runtime scope is correct — not needed at compile time.

Spring JDBC — one step up

Spring JDBC is a thin convenience layer on top of raw JDBC. It does not add ORM — you still write SQL. But it eliminates all the boilerplate.

Raw JDBC — you manage everything

Open connection manually

Create PreparedStatement manually

Iterate ResultSet manually

Close all resources in finally block

Translate SQLExceptions manually

Spring JDBC — Spring manages the ceremony

Spring opens and closes connections

Spring handles exceptions

Spring cleans up resources

You only provide: SQL + row mapping logic

// Spring JDBC — JdbcTemplate
@Autowired
private JdbcTemplate jdbcTemplate;

// Query — no connection, no ResultSet, no close()
List<User> users = jdbcTemplate.query(
    "SELECT * FROM users WHERE id = ?",
    (rs, rowNum) -> {
        User u = new User();
        u.setId(rs.getLong("id"));
        u.setName(rs.getString("name"));
        return u;
    },
    1L
);

// Update — same simplicity
jdbcTemplate.update(
    "INSERT INTO users(id, name) VALUES (?, ?)",
    user.getId(), user.getName()
);
⚠️
Spring JDBC still requires SQL

Spring JDBC reduces boilerplate but you still write every SQL query yourself. The row mapping from ResultSet to your object is still manual. This is why ORM (Hibernate) was invented on top of it.

Spring Boot/Data / JPA
Hibernate
The ORM framework that generates SQL so you don't have to

What is Hibernate?

Hibernate is the most popular Java ORM framework. You annotate your Java class, and Hibernate takes full responsibility for generating SQL, executing it, and converting the results back into objects.

What Hibernate does for you
  • Reads your @Entity classes
  • Generates INSERT / UPDATE / DELETE / SELECT SQL
  • Executes SQL via JDBC underneath
  • Maps result rows back to objects
  • Manages relationships (@OneToMany etc)
  • First-level cache — avoids redundant DB hits
What you do
  • Annotate the class with @Entity
  • Mark the primary key with @Id
  • Call entityManager.persist(user)
  • Everything else is Hibernate's job

Entity — your Java class mapped to a table

@Entity                    // tells Hibernate: map this class to a DB table
@Table(name = "users")    // optional — defaults to class name lowercase
public class User {

    @Id                        // primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // auto-increment
    private Long id;

    @Column(name = "name")   // optional — defaults to field name
    private String name;

    // getters and setters
}

This is all the information Hibernate needs. It reads the annotations once at startup and builds an internal map:

Hibernate reads annotations and creates this mapping internally:

User.class  ↔  users (table)
User.id       ↔  id (column, primary key)
User.name     ↔  name (column)

How Hibernate translates operations

// You write:
entityManager.persist(user);

// Hibernate generates and executes:
INSERT INTO users (name) VALUES ('Ishant')

// You write:
entityManager.find(User.class, 1L);

// Hibernate generates:
SELECT id, name FROM users WHERE id = 1

// You write:
entityManager.remove(user);

// Hibernate generates:
DELETE FROM users WHERE id = 1

How Hibernate works internally

There are two phases — startup (one time) and runtime (every request).

Startup — happens once when your app boots

Spring Boot starts
↓
Hibernate scans for @Entity classes
↓
Reads annotations — builds class-to-table mapping metadata
↓
Creates SessionFactory (the heavy, one-time setup object)
↓
App is ready — all mappings cached in memory

Runtime — every time you do a DB operation

entityManager.persist(user)
↓
Hibernate looks up mapping: User → users table
↓
Generates SQL: INSERT INTO users (name) VALUES (?)
↓
Passes to JDBC with parameter values
↓
JDBC Driver sends to database
↓
Row written to DB

Relationship annotations

One of Hibernate's biggest wins — relationships that would require manual JOINs in SQL are expressed as simple annotations.

@Entity
public class User {
    @Id
    private Long id;
    private String name;

    @OneToMany(mappedBy = "user")   // one user → many transactions
    private List<Transaction> transactions;
}

@Entity
public class Transaction {
    @Id
    private Long id;
    private Double amount;

    @ManyToOne                          // many transactions → one user
    @JoinColumn(name = "user_id")      // foreign key column name
    private User user;
}
💡
Hibernate sits on top of JDBC

Hibernate does not bypass JDBC. It generates SQL and then uses JDBC to execute it. The JDBC driver is still there at the bottom doing the actual network communication with the database.

Spring Boot/Data / JPA
JPA & Spring Data JPA
The specification layer and the repository abstraction on top

What is JPA?

JPA (Java Persistence API) is a specification — not an implementation. It defines a standard set of annotations and interfaces that any ORM framework must implement.

⚠️
Common misconception — JPA ≠ ORM

JPA does not do any work. It only defines rules. Hibernate is the one that actually reads your annotations and generates SQL. JPA is the contract; Hibernate is the contractor.

JPA (Specification)

Defines what must exist

@Entity, @Id, @OneToMany

EntityManager interface

persist(), find(), remove()

Just a set of rules — no runnable code

Hibernate (Implementation)

Defines how it actually works

Implements every JPA annotation

Provides EntityManager implementation

Actually generates and runs SQL

Runnable code — the real engine

The List / ArrayList analogy

// In Java collections:
List<String> list = new ArrayList<>();
//  ↑ specification        ↑ implementation

// In JPA:
EntityManager em = // ...obtained from Spring
//  ↑ JPA interface    ↑ Hibernate provides the actual object

Why was JPA created?

Before JPA, every ORM framework had its own API. Hibernate had its own Session API. EclipseLink had different classes. If you wanted to switch ORM frameworks, you had to rewrite a large portion of your codebase.

Your code uses: EntityManager (JPA standard)
↓
at runtime, Spring injects whichever implementation you have on the classpath
↓
Hibernate EclipseLink OpenJPA

You swap the dependency in pom.xml — your code stays identical. JPA is the reason this works.

What is Spring Data JPA?

Even writing entityManager.persist(user) and entityManager.find(User.class, id) for every entity became repetitive. Spring Data JPA removes even that.

1
You declare an interface — nothing else 
public interface UserRepository
    extends JpaRepository<User, Long> {
    // completely empty — no code needed
}
2
Spring generates the implementation at startup

Spring sees your interface, sees it extends JpaRepository, and automatically creates a full implementation class behind the scenes. You never write it.

3
You get dozens of methods for free 
userRepository.save(user);           // INSERT or UPDATE
userRepository.findById(1L);        // SELECT WHERE id = 1
userRepository.findAll();             // SELECT * FROM users
userRepository.deleteById(1L);      // DELETE WHERE id = 1
userRepository.count();              // SELECT COUNT(*)

Query methods — just by naming the method

Spring Data JPA can generate SQL from the method name itself — no SQL, no annotations needed.

public interface UserRepository extends JpaRepository<User, Long> {

    // Spring generates: SELECT * FROM users WHERE name = ?
    List<User> findByName(String name);

    // Spring generates: SELECT * FROM users WHERE email = ? AND active = ?
    Optional<User> findByEmailAndActive(String email, boolean active);

    // Custom SQL when naming won't cut it
    @Query("SELECT u FROM User u WHERE u.createdAt > :date")
    List<User> findUsersCreatedAfter(@Param("date") LocalDate date);
}

How Spring connects to the database — end to end

When your Spring Boot app starts, a precise sequence happens before your code can do any DB operation. Here it is in full.

application.properties — what you provide

# Tell Spring where the database is and how to connect
spring.datasource.url=jdbc:h2:mem:testdb       # connection URL
spring.datasource.username=sa                  # DB username
spring.datasource.password=                    # DB password (empty for H2)
spring.datasource.driver-class-name=org.h2.Driver  # driver class

# Tell Hibernate how to behave
spring.jpa.hibernate.ddl-auto=update           # create/update tables on startup
spring.jpa.show-sql=true                       # print generated SQL to console

URL anatomy

jdbc:h2:mem:testdb
 ↑     ↑   ↑   ↑
 │     │   │   └── database name
 │     │   └────── mem = in-memory (gone when app stops)
 │     └────────── which database (h2 / postgresql / mysql)
 └──────────────── tells Java: use JDBC protocol

What Spring does with those properties — startup sequence

1
Reads datasource properties

Spring Boot reads spring.datasource.* from application.properties.

2
Loads the JDBC Driver

Loads org.h2.Driver (or whichever you specified). This is the translator that knows how to talk to your specific database.

3
Creates a DataSource with a connection pool (HikariCP)

Spring does not open one connection and keep it. It creates a pool of pre-opened connections managed by HikariCP (the default). When your code needs a connection it borrows one from the pool and returns it after the query — much faster than opening a new connection every time.

// HikariCP pool — visualised
Pool: [ conn1 | conn2 | conn3 | conn4 | conn5 ... conn10 ]
       ↑ idle, ready to use

Request comes in → borrow conn1 → run query → return conn1 to pool
4
Creates EntityManagerFactory

Hibernate uses this factory to create EntityManager instances per request. Think of it as the master configuration object for Hibernate.

5
Hibernate scans @Entity classes

Scans your project for @Entity classes, reads annotations, builds class-to-table mappings. If ddl-auto=update, creates or updates DB tables to match your entities.

6
Spring generates Repository implementations

For every interface that extends JpaRepository, Spring generates a concrete implementation class at runtime. Your UserRepository bean is now ready.

Spring Boot/File Management
Multipart & File Upload
A story — follow movie.mp4 from the browser all the way to your controller

Chapter 1  ·  The browser has a problem

Imagine you are building a Video Management System. A user wants to upload movie.mp4. The browser needs to send both some text and a binary video file together in one HTTP request.

If it were only text, a plain JSON request would work perfectly:

{
  "title": "Spring Tutorial"
}

But the video is a binary file. One option is to base64-encode it and stuff it inside JSON:

{
  "title": "Spring Tutorial",
  "video": "AABB99FF2D3E..."   ← base64 encoded binary
}

But this is a terrible idea for large files:

300 MB video
↓  base64 encoding adds ~33% overhead
~400 MB over the wire
+ extra CPU on both ends to encode and decode

So the browser reaches for a different content type:

Content-Type: multipart/form-data

Chapter 2  ·  What is multipart?

The browser says: "I don't want to send one big JSON document. I want to send multiple independent pieces of data in the same request."

So it creates a multipart request — one request body, but divided into separate independent sections:

One HTTP request body

├── Part 1  →  title = "Spring Tutorial"
└── Part 2  →  video = movie.mp4 (raw binary)

Hence the name: multi + part.

Chapter 3  ·  The boundary appears

Now the browser has a new problem. Multiple parts are packed into one body. How will the server know where one part ends and the next begins?

The browser generates a special delimiter called a boundary — a long random string unlikely to appear inside the uploaded file — and includes it in the Content-Type header:

Content-Type: multipart/form-data; boundary=ABC123

The request body then looks like this:

--ABC123                              ← start of part 1
Content-Disposition: form-data; name="title"

Spring Tutorial

--ABC123                              ← end of part 1 / start of part 2
Content-Disposition: form-data; name="video"; filename="movie.mp4"
Content-Type: video/mp4

(raw binary bytes...)

--ABC123--                            ← double dash = no more parts
💡
Analogy — chapter separators in a book

Think of the boundary like chapter dividers. Each --ABC123 line says "new section starts here". The --ABC123-- with the double dash at the end says "the book is finished." The browser generates this string automatically — you never write it yourself.

Chapter 4  ·  The request reaches Tomcat

The HTTP request arrives at Tomcat. Tomcat sees Content-Type: multipart/form-data and thinks: "Ah, this is a multipart request."

But before it starts parsing, it asks itself some configuration questions:

Questions Tomcat asks
  • Where should I store temp files?
  • What is the maximum file size?
  • What is the maximum request size?
  • How much can I hold in memory?
Answers come from
  • MultipartConfigElement
  • Spring Boot creates it automatically
  • You just set properties
  • No manual bean creation needed

Chapter 5  ·  MultipartConfigElement — the rulebook

MultipartConfigElement is not responsible for parsing. It is purely a configuration object — a rulebook that tells Tomcat what is and isn't allowed.

In Spring Boot you never touch this class directly. You just set two lines in application.properties and Spring Boot creates the bean automatically:

# application.properties
spring.servlet.multipart.max-file-size=500MB      # max size of a single file
spring.servlet.multipart.max-request-size=500MB   # max size of the whole request
spring.servlet.multipart.enabled=true             # already true by default
💡
Spring Boot does the wiring

The moment Spring Boot reads these properties, it creates and registers a MultipartConfigElement bean behind the scenes. You never instantiate it — the properties file is all the configuration you need.

Chapter 6  ·  Tomcat opens the package

With the rulebook in hand, Tomcat parses the request body using the boundary as a delimiter. It splits the raw bytes into separate pieces and wraps each one in a Part object from the Servlet API:

// Tomcat creates these Servlet API objects:
Part titlePart;   // contains "Spring Tutorial"
Part videoPart;   // contains the raw binary bytes of movie.mp4

At this point Tomcat's job is mostly done. It has unpackaged the envelope and handed out the contents. Now Spring takes over.

Chapter 7  ·  Spring enters the story

Spring looks at the raw Part objects Tomcat produced and says: "These Servlet API objects are low-level and not developer-friendly. Let me convert them into something easier to work with."

This conversion is the job of MultipartResolver:

Tomcat  →  Part titlePart, Part videoPart
              ↑ Servlet API — low level
↓  MultipartResolver wraps each Part
Spring  →  String title, MultipartFile video
              ↑ Spring API — clean and easy

Chapter 8  ·  Birth of MultipartFile

Spring creates a MultipartFile — its clean abstraction for an uploaded file. It is not a network concept or a protocol. It is simply a convenient Java object that wraps the raw file data and gives you useful methods.

// Everything you need about the uploaded file:
video.getOriginalFilename();          // → "movie.mp4"
video.getContentType();               // → "video/mp4"
video.getSize();                      // → 104857600  (bytes)
video.isEmpty();                      // → false

// Reading the bytes — pick based on file size:
InputStream stream = video.getInputStream();   // ✅ always safe — streams, doesn't load all at once
byte[] data = video.getBytes();                // ⚠️  small files only — entire file into memory

// Save directly to disk:
video.transferTo(Path.of("/uploads/movie.mp4"));
⚠️
Never use getBytes() for large files

A 500 MB video becomes 500 MB on the Java heap instantly. Always use getInputStream() and stream the bytes to your storage layer.

Chapter 9  ·  Understanding @RequestBody

Let's step back from video uploads for a moment. Consider a plain JSON request:

POST /videos   Content-Type: application/json

{
  "title": "Spring Tutorial"
}

The body contains one JSON document. Spring can take the entire body and hand it to Jackson to deserialize into a Java object:

@PostMapping
public void create(@RequestBody VideoRequest request) { }
//               ↑ "take the ENTIRE HTTP body and convert to VideoRequest"

Chapter 10  ·  Why @RequestBody fails for multipart

Now look at a multipart request. The body is not a single JSON document — it is multiple independent parts:

HTTP body
├── Part(title) = "Spring Tutorial"
└── Part(video) = (binary bytes)

If Spring sees @RequestBody here, it gets confused:

// Spring asks:
// "What exactly should I deserialize?"
// "The title part? The video part? The entire multipart structure?"
// There is no obvious answer. @RequestBody expects ONE body → ONE object.
// Multipart gives MANY parts. The shapes don't match.

Chapter 11  ·  Why @RequestParam works

After Tomcat has parsed the multipart request into parts, Spring can bind each part individually by name. @RequestParam says: "Give me the part named 'title'. Give me the part named 'video'."

@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public void upload(
    @RequestParam String title,         // title part → String
    @RequestParam MultipartFile video    // video part → MultipartFile
) { }
💡
@RequestParam is not just for query parameters

The name suggests it only works for URL query params like ?title=foo. But Spring also uses it to bind individual multipart parts. Same annotation, two different contexts.

Chapter 12  ·  Enter @RequestPart

One day requirements change. Instead of a plain text title, the client now sends a full JSON metadata object as one of the parts alongside the video:

-- Part 1: metadata (JSON)
{
  "title": "Spring Tutorial",
  "duration": 120
}

-- Part 2: video (binary)
(raw bytes of movie.mp4)

@RequestParam treats everything as a simple string or file. To tell Spring "this part is JSON — run it through Jackson and give me a Java object", you use @RequestPart:

@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public void upload(
    @RequestPart VideoMetadata metadata,   // JSON part → Jackson → Java object
    @RequestPart MultipartFile video        // binary part → MultipartFile
) { }

public class VideoMetadata {
    private String title;
    private Integer duration;
}

Chapter 13  ·  The complete journey

Here is the full path movie.mp4 travels from the moment the user clicks Upload to the moment your controller method runs.

User clicks Upload — browser submits the form
↓
Browser packages data as multipart/form-data with boundary
↓
Tomcat receives raw bytes
↓ MultipartConfigElement limits checked here
Tomcat splits body by boundary → creates Servlet Part objects
↓
Spring's MultipartResolver wraps Part → MultipartFile
↓
@RequestParam / @RequestPart binds each part to your method params
↓
Your controller method runs with String title + MultipartFile video
↓
Service layer saves to S3 / MinIO / local disk

The three rules to remember

1
Entire request body is one JSON object → @RequestBody 
@PostMapping
public void create(@RequestBody VideoRequest req) { }
2
Multipart with simple text fields or a file → @RequestParam 
@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public void upload(
    @RequestParam String title,
    @RequestParam MultipartFile video
) { }
3
One multipart section is itself JSON → @RequestPart 
@PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public void upload(
    @RequestPart VideoMetadata metadata,
    @RequestPart MultipartFile video
) { }

Final mental model

JSON request
One body = one JSON doc
↓
@RequestBody
↓
Java object via Jackson
Multipart request
One body = many parts
↓
@RequestParam / @RequestPart
↓
String / MultipartFile / DTO
✅
The one sentence to remember

@RequestBody works on the entire request body. @RequestParam and @RequestPart work on individual parts inside a multipart body. MultipartFile is Spring's clean wrapper around an uploaded file after Tomcat and Spring have already done all the parsing.

File Validation
The story continues — a senior engineer asks one question that changes everything

Chapter 14  ·  The senior engineer's question

You've just built your upload endpoint and you're feeling good about it:

@PostMapping("/videos")
public void upload(@RequestParam MultipartFile video) {
    // save the video...
}

A senior engineer walks over and asks: "What validations have you added?"

You say: "It's just a video upload. Why do I need validation?"

The senior smiles. "Let's see what happens."

What follows is a series of discoveries — each one revealing a new reason validation exists.

Chapter 15  ·  Discovery 1 — Correctness

The first user opens your upload page, accidentally clicks Upload without selecting a file, and your server receives a MultipartFile where video.isEmpty() == true.

Without validation, the upload "succeeds". A record is created in the database pointing to a file that doesn't exist.

💡
Not all validation is about security

Some validation is simply about correctness — did the user actually do what they intended to do? An empty file is not an attack, it's an accident. You still need to catch it.

// First validation — is there actually a file?
if (video == null || video.isEmpty()) {
    throw new ValidationException("No file provided");
}

Chapter 16  ·  Discovery 2 — Resource protection

The next user uploads a 50 GB video. Your server starts processing it. Disk fills up. Memory pressure spikes. Other requests slow to a crawl. The server is struggling because of one file.

50 GB video arrives
↓
Disk fills up
Memory pressure increases
Other users' requests slow down
↓
Server effectively unavailable

The fix is two lines in application.properties — Tomcat rejects oversized requests before they even reach your controller:

spring.servlet.multipart.max-file-size=500MB      # per file
spring.servlet.multipart.max-request-size=500MB   # total request
⚠️
These limits live in Tomcat, not your controller

If the file exceeds these limits, Tomcat rejects the request and your controller code never runs. You handle this by catching MaxUploadSizeExceededException in a @ControllerAdvice.

Chapter 17  ·  Discovery 3 — Security (and the lie)

You add extension validation:

// Check extension — seems reasonable?
String filename = video.getOriginalFilename();
if (!filename.endsWith(".mp4")) {
    throw new ValidationException("Only MP4 allowed");
}

Someone points out: "A filename is just a label." Anyone can rename virus.exe to movie.mp4. Your check passes.

So you add MIME type validation:

// Check MIME type — better?
if (!"video/mp4".equals(video.getContentType())) {
    throw new ValidationException("Invalid file type");
}

You feel safe. For about five minutes — until you learn what an attacker does.

Attacker's curl command:
curl -F "video=@virus.exe;type=video/mp4" http://your-api/videos
                                      ↑ manually overriding the Content-Type header

What Spring sees:
video.getContentType() → "video/mp4"  ← the lie succeeds

Result:
Validation passes. virus.exe is stored on your server.
🚨
The crucial lesson — MIME type is also client-supplied

The Content-Type header is sent by the client. The client can put anything there. Both the filename and the MIME type are just labels — labels the client writes. Neither proves what the file actually contains.

The package analogy

Filename + MIME type

Like the label on a package that says "Contains: Chocolate"

The sender wrote that label

The package could contain chocolate — or a brick

You only know what the sender claimed

Actual bytes (Apache Tika)

Like opening the package and looking inside

You inspect the actual contents

The sender's label is irrelevant

Reality is the source of truth

Chapter 18  ·  Discovery 4 — Apache Tika reads the bytes

Every file format leaves a fingerprint in its first few bytes. These are called magic bytes. Tika inspects these bytes directly — it doesn't care what the filename says or what the client put in the Content-Type header.

Executable (.exe)
MZ...rest of file
PDF
%PDF...rest of file
MP4 video
ftyp...rest of file
↑ These magic bytes are written by the program that created the file — not by the user. They can't be spoofed by renaming. 
<!-- pom.xml -->
<dependency>
    <groupId>org.apache.tika</groupId>
    <artifactId>tika-core</artifactId>
    <version>2.9.1</version>
</dependency>
// Apache Tika — reads actual bytes, ignores the label
Tika tika = new Tika();
String detectedType = tika.detect(video.getInputStream());
// → "video/mp4"        for a real MP4
// → "application/x-dosexec"  for a renamed .exe
// → "application/pdf"  for a renamed PDF

if (!"video/mp4".equals(detectedType)) {
    throw new ValidationException("File is not a real MP4");
}
✅
Trust ranking

Actual bytes (Tika) > MIME type > Filename extension
The bytes are written by the program that created the file. The MIME type and filename are written by the user. Always trust what's inside over what the label says.

Chapter 19  ·  Discovery 5 — Business rules

Finally the product team joins: "We only support MP4. Maximum 500 MB. No other formats."

These are not security concerns. They are not correctness concerns. They are business requirements — rules specific to your product.

Examples of business rules
  • Only MP4 or MOV — no AVI, no WMV
  • Maximum 500 MB per video
  • Only PNG images — no JPG
  • PDF attachments only, max 10 MB
Where they live
  • Usually as constants in a validator class
  • Or in application.properties for configurability
  • Every application defines its own
  • Can change — easy to update in one place
// Business rule — allowed types from config
private static final Set<String> ALLOWED_TYPES =
    Set.of("video/mp4", "video/quicktime");

private static final long MAX_SIZE = 500L * 1024 * 1024; // 500 MB

if (!ALLOWED_TYPES.contains(detectedType)) {
    throw new ValidationException("Unsupported format");
}
if (video.getSize() > MAX_SIZE) {
    throw new ValidationException("File too large");
}

Chapter 20  ·  The four reasons validation exists

1 · Correctness
  • Did the user actually send a file?
  • video.isEmpty()
  • Not security — just accuracy
2 · Resource protection
  • Prevents disk / memory exhaustion
  • max-file-size in properties
  • Protects all users, not just one
3 · Security
  • Extension check — weak, but a start
  • MIME check — better, still spoofable
  • Tika bytes — the real truth
4 · Business rules
  • Only specific formats allowed
  • Specific size limits
  • Product-defined requirements

Chapter 21  ·  The production validation flow

A well-built upload endpoint runs validations in a specific order — cheapest checks first, most expensive last.

Receive MultipartFile from controller
↓
① File exists and is not empty  — correctness
↓
② Size within limits  — resource protection (already enforced by Tomcat)
↓
③ Extension check  — security, first layer (weak but fast)
↓
④ MIME type check  — security, second layer (spoofable but worth checking)
↓
⑤ Apache Tika byte inspection  — security, ground truth
↓
⑥ Business rules  — allowed formats, custom size limits
↓
All checks passed → store the file

Putting it all together — a production validator

@Component
public class VideoFileValidator {

    private static final Set<String> ALLOWED_EXTENSIONS =
        Set.of("mp4", "mov");

    private static final Set<String> ALLOWED_MIME_TYPES =
        Set.of("video/mp4", "video/quicktime");

    private static final long MAX_BYTES =
        500L * 1024 * 1024;  // 500 MB

    private final Tika tika = new Tika();

    public void validate(MultipartFile file) {

        // ① Correctness — did a file actually arrive?
        if (file == null || file.isEmpty()) {
            throw new ValidationException("No file provided");
        }

        // ② Resource — size check (belt + suspenders over the Tomcat limit)
        if (file.getSize() > MAX_BYTES) {
            throw new ValidationException("File exceeds 500 MB");
        }

        // ③ Security — extension (weak, but an extra layer)
        String original = file.getOriginalFilename();
        String ext = original != null
            ? original.substring(original.lastIndexOf('.') + 1).toLowerCase()
            : "";
        if (!ALLOWED_EXTENSIONS.contains(ext)) {
            throw new ValidationException("Invalid file extension");
        }

        // ④ Security — MIME type from client (still spoofable, still worth checking)
        if (!ALLOWED_MIME_TYPES.contains(file.getContentType())) {
            throw new ValidationException("Invalid content type");
        }

        // ⑤ Security — Apache Tika: inspect the actual bytes (ground truth)
        try {
            String detected = tika.detect(file.getInputStream());
            if (!ALLOWED_MIME_TYPES.contains(detected)) {
                throw new ValidationException("File content does not match declared type");
            }
        } catch (IOException e) {
            throw new ValidationException("Could not inspect file");
        }
    }
}

The golden rule

The biggest lesson from file validation is not about Spring or Tika. It is this:

Everything sent by a client is untrusted:

Filename Content-Type header JSON fields Query parameters Cookies
The backend's job is always:

Receive input ↓
Validate input ↓
Process input
🔐
Never trust the client

File validation exists to ensure correctness, protect system resources, enforce business rules, and defend against untrusted clients who may — accidentally or intentionally — send invalid files. The only thing you can trust is what you verify yourself.

Spring Boot/File Management
Metadata Modelling
A story — one question after upload changes how you think about data forever

Chapter 1  ·  The first upload

You have finally built your upload endpoint. A user uploads spring-tutorial.mp4. The request reaches your controller. You receive a MultipartFile and successfully store the file. At this point, you feel the problem is solved.

Then someone asks: "How will you find this video later?"

You think: "I'll just read the file."

Then another question comes: "How will you show all videos uploaded by a specific user?"

You realise — the file itself doesn't answer those questions. The file only contains video bytes. You need information about the video.

Chapter 2  ·  Meeting metadata

Imagine a physical book in a library. The actual book contains pages, text, and images. But the library also maintains a catalogue card — it holds the book name, author, shelf location, and published date.

The catalogue card is not the book. It is information about the book. This is metadata.

Video file — Data

Frames, audio, binary bytes

The actual content

Lives in storage (S3 / Disk / MinIO)

You must open it to know anything about it

Metadata — Data about data

Video ID, filename, upload time, owner, size, status

Information about the video

Lives in the database

Enables search, listing, filtering — without opening the file

Chapter 3  ·  The realization

Suppose a user uploads movie.mp4. The video itself contains frames, audio, and binary bytes. But your application needs to know things like: the video ID, the filename, when it was uploaded, who uploaded it, how large it is, what its current status is, and where it is stored. None of these things are part of the actual video. Yet they are essential for the application.

⚠️
The key insight

Video content and video metadata are two completely different things. The video lives in storage. The metadata lives in the database.

Chapter 4  ·  The great separation

A beginner often imagines the database simply stores the video. In reality, most systems keep these two concerns entirely separate.

Video file
movie.mp4
↓
S3 / MinIO / Disk
s3://videos/uploads/movie.mp4
Metadata
id · filename · size · uploadedBy · ...
↓
Database (PostgreSQL / MySQL)

The database does not store the video. It stores information about the video — things like the ID, filename, size, upload date, and uploader. The database row is the catalogue card; the S3 object is the actual book.

Chapter 5  ·  What is metadata modelling?

Once the team starts designing the system, someone asks: "What metadata should we store?" The process of answering that question — deciding which fields to track, why each one exists, and how the model should grow over time — is called metadata modelling.

💡
Definition

Metadata modelling means designing what information about a video should exist in the system — separate from the actual video content.

Chapter 6  ·  Business metadata vs technical metadata

As the model grows, you will notice that metadata naturally splits into two categories.

Business metadata

Describes how the business sees the video. Comes from user input or product requirements.

Examples: title, description, visibility (public / private / unlisted), tags, category

These fields don't describe the file format — they describe the video's role in the product.

Technical metadata

Describes the file itself. Comes from the file or the processing pipeline.

Examples: file size, content type, duration, resolution, codec, frame rate, bitrate

These fields describe the actual media — what it is and how it is encoded.

Chapter 7  ·  Upload-time metadata vs generated metadata

An important design distinction — some metadata is available the moment the upload arrives, and some requires inspecting the video file after it has been stored.

Known at upload time
Filename Content-Type File size (bytes) Upload timestamp Uploader (userId)
Generated after processing
Duration Resolution Codec Frame rate Thumbnail URL

To obtain generated metadata, the system must inspect the video after it is stored. The tools commonly used for this are FFmpeg and MediaInfo — they read duration, resolution, codec, and frame rate from the file and write the results back into your metadata record.

Chapter 8  ·  Why metadata exists — the performance argument

Suppose the product asks: "Show all videos uploaded today."

Without metadata

Open every file in storage, inspect each one to determine its upload date, then filter the results. This is extremely expensive and does not scale.

With metadata

Run a single indexed SQL query against the database. Returns results in milliseconds even at millions of rows.

Metadata enables searching, filtering, sorting, pagination, ownership checks, status tracking, and reporting — all without touching the actual file content.

Chapter 9  ·  Status — metadata about lifecycle

When uploads become asynchronous, the system needs to track where in the pipeline each video currently is. This is also metadata — it describes the state of the video, not its content.

User uploads file  →  UPLOADING
↓
File stored in S3  →  PROCESSING
↓
FFmpeg extracts duration, resolution, thumbnail
↓
All done  →  READY
Something fails  →  FAILED

The four states — UPLOADING, PROCESSING, READY, and FAILED — live as an enum field on the metadata entity. They let the system (and the user) know what stage the video is in without ever touching the file.

Chapter 10  ·  Storage metadata

When the team migrates to S3, the metadata model also needs to record where the file now lives inside the bucket. You need two new fields: the bucket name and the object key (the path within that bucket). This is another form of metadata — it tells the application how to locate the actual file without hardcoding any paths.

Chapter 11  ·  How to think like a system designer

When deciding what to put in your metadata model, ask a single question for every piece of information you might need:

💡
The designer's question

"What information does the application need without opening the actual file?"

Every answer to that question is a metadata candidate. Who uploaded it? When? Can users view it? Where is it stored? What is its size? How long is it? If the app needs to know it without reading bytes, it belongs in the database as metadata.

A realistic first version of a video metadata entity would include the following fields, each present for a specific reason:

Spring Boot/REST APIs
DTO Validation
Bean Validation in Spring Boot — verifying incoming data before it enters the application

Why validation exists

Once you have a working API endpoint that accepts a @RequestBody DTO, that DTO will accept anything by default — empty strings, nulls, negative numbers, invalid emails. Without validation, your database silently fills with garbage data.

Without validation

Title = "", null, or "   " all get saved to the database

Duration = -500 is accepted without complaint

Business logic runs on data it should never have seen

With validation

Invalid requests are rejected at the controller boundary with 400 Bad Request

The service layer only ever receives clean, rule-conforming data

Rules live on the DTO itself — no scattered if-null checks

⚠️
Clients are untrusted

Just as users can upload invalid files, they can also send {"title": "", "duration": -500}. The backend must always validate what it receives — never assume the client sent something correct.

The two gates

A video upload request carries two payloads — a file and a metadata DTO. Each has its own validation gate. Both must pass before the request proceeds.

Gate 1 — DTO Validation
Title present? Visibility provided? Description length valid? Duration positive?
Gate 2 — File Validation
File present? Correct MIME type? Size within limit? Content actually valid?
Both gates pass
↓
Controller → Service → Storage

How Bean Validation works in Spring

Spring integrates with the Jakarta Bean Validation API. Instead of writing manual null checks everywhere, you declare rules directly on DTO fields using annotations. Then you add a single @Valid on the controller parameter to tell Spring to enforce those rules before the method body runs.

1
Annotate the DTO fields with constraint rules 
public class CreateVideoRequest {

    @NotBlank
    @Size(max = 100)
    private String title;

    @Size(max = 500)
    private String description;

    @Positive
    private Integer duration;
}
2
Add @Valid on the controller parameter — this is what triggers validation 
@PostMapping
public void createVideo(
        @RequestBody @Valid CreateVideoRequest request) {

    videoService.create(request);
}
3
Spring throws MethodArgumentNotValidException automatically if any constraint fails

The request never reaches the service layer. Spring returns 400 Bad Request before your business logic runs.

🚨
The most common mistake — forgetting @Valid

You can annotate every field perfectly with @NotBlank, @Size, and @Positive, and validation will silently do nothing if @Valid is missing from the controller parameter. The annotations alone are just metadata — @Valid is the trigger that tells Spring to actually run the checks.

Request flow — with vs without @Valid

Without @Valid
HTTP Request arrives
↓
DTO object created
↓
Controller executes immediately
↓
Invalid data reaches service
With @Valid
HTTP Request arrives
↓
DTO object created
↓
Bean Validation runs
  @NotBlank · @Size · @Positive · ...
↓
Fail → 400 Bad Request (never reaches service)
↓
Pass → Controller executes
↓
Clean data enters service layer

@NotNull vs @NotEmpty vs @NotBlank

These three annotations look similar but catch different levels of "bad" input. For user-entered strings, @NotBlank is almost always what you want.

Annotation Rejects Accepts Use when
@NotNull null ""   "   " Field must be present but can be empty (e.g. an object reference)
@NotEmpty null   "" "   " At least one character is required (spaces count)
@NotBlank null   ""   "   " "Spring Tutorial" Actual meaningful text required — best choice for user-entered strings

Validating nested DTOs

When your DTO contains another DTO as a field, adding @Valid on the controller alone is not enough. The nested object also needs @Valid on its field declaration, otherwise Spring will not descend into it.

Broken — nested DTO not validated
public class CreateVideoRequest {

    // @Valid missing here!
    private OwnerRequest owner;
}
Correct — @Valid on the nested field
public class CreateVideoRequest {

    @Valid
    private OwnerRequest owner;
}
